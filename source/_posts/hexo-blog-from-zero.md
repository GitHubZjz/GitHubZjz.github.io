## 一、为什么要搭这个博客：整体规划与目标

最近在公司做官网项目（纯静态企业站），从图片压缩、性能优化到部署方案，积累了一套完整的建站经验。过程中我发现一个问题：**这些经验散落在日报、AI 对话记录和自己的备忘里，没有沉淀成可检索、可复用的资产**。

所以我想搭一个个人博客，目标是：

1. **输入成本极低**——直接写 Markdown 就能发布，日报、和 AI 讨论的技术方案、踩坑记录，整理一下就是一篇文章；
2. **成本极低**——个人博客访问量不大，不想为它付出持续的金钱成本；
3. **源码在自己手里**——数据自主，随时可迁移，不被任何平台绑架；
4. **够用就行**——不追求高并发高可用，能稳定打开、能被搜索引擎收录即可。

带着这四个目标，我先做了一轮技术选型。

## 二、技术选型：思考过程与决策依据

### 2.1 写作方式决定架构

博客的核心矛盾是"内容要频繁更新"和"不想每次手写 HTML"。我列了四个候选：

| 方案 | 写文章方式 | 技术栈 | 年成本 | 结论 |
|---|---|---|---|---|
| **Hexo** | 写 Markdown 文件 | Node.js | 0~44 元 | ✅ 与我的工作流完全匹配 |
| Hugo | 写 Markdown 文件 | Go | 同上 | 备选，生态略小 |
| WordPress | 浏览器后台写 | PHP + MySQL | 300~500 元 | 对我过重 |
| 纯手写 HTML | 手写 HTML | 无 | 0 元 | 每篇手动排目录/归档，不可持续 |

**选 Hexo 的决定性理由**：我已经习惯用 Markdown 写日报和总结，Hexo 把"写一个 .md 文件"直接变成"发布一篇文章"，文章页、分类页、标签页、归档页、RSS、sitemap 全部自动生成——这些自己手写要几百行代码的工作，Hexo 一条命令完成。

**放弃 WordPress 的理由**：它的核心优势是"非技术人员在后台改内容"，但我的博客作者是我自己，用不上；代价却是要学 PHP、维护数据库、定期更新插件防漏洞。我的内容更新频率（每周几篇）完全撑不起这套重架构。

### 2.2 托管方案：GitHub Pages 完胜

| 环节 | 国内 OSS 方案 | GitHub Pages |
|---|---|---|
| ICP 备案 | 必须，2~3 周 | **不需要**（服务器在海外） |
| 公安联网备案 | 必须 | 不需要 |
| 服务器费用 | 需要 | **0 元** |
| SSL 证书 | 免费申请 | 自动配好 HTTPS |
| 域名 | 必须 | 可先用免费二级域名 |

虽然国内访问 github.io 偶尔不稳定，但我的诉求就是"能打开就行"，**总成本 0 元、当天上线**——没有理由选别的。以后真嫌慢，买个 38 元/年的 .cn 域名绑上去，还能绕开 DNS 污染，这是后话。

### 2.3 顺便算过一笔账

调研时对比了朋友的凡科建站。他说的"买断"，应是指**买断模板/产品的使用权**——一次付费，终身使用该版本的模板与编辑器，而不是买断服务器。事实上服务器始终在凡科云端（多站共享的托管环境），每年仍需缴纳云托管费（首年免费，次年起约百元），源码也拿不到。对比年费制（698 元/年起），买断省掉的是"产品续费"这一层，但托管年费与平台绑定依然存在——本质仍是"租"平台，只是把租金的一部分一次性预付了。而 Hexo + GitHub Pages 是 0 元，源码 100% 归自己。**SaaS 建站卖的是省心，静态站生成器卖的是自由**——对会点技术的个人，后者显然更划算。

## 三、动手开发：具体步骤与关键操作

### 3.1 环境准备

机器上用 nvm 管理多个 Node 版本（16/18/20/22 都有）。Hexo 8.x 要求 Node ≥ 20.19，切到 22.22.0：

```powershell
nvm use 22.22.0
node -v   # v22.22.0
```

机器上早已囤了 16/18/20/22 好几个版本，nvm 一条命令随切随用——多版本管理在这一步帮了大忙：

![nvm list：本机的多版本 Node 列表](nvm-list.png)

### 3.2 配置 npm（国内环境必做）

```powershell
# 换国内镜像，下载速度从分钟级降到秒级
npm config set registry https://registry.npmmirror.com

# C 盘空间紧张，把 npm 缓存迁到 D 盘
npm cache clean --force
npm config set cache "D:\npm-cache"
```

一个小提示：`npm config set` 这类命令**静默执行、没有任何输出就是成功**，别把"没反应"当成失败。

### 3.3 安装与初始化

```powershell
npm install -g hexo-cli    # 全局安装，54 个依赖 6 秒装完
hexo -v                    # 验证：hexo-cli 4.3.2 / node 22.22.0

cd D:\projects             # 先切目录！博客会建在"当前目录"下
hexo init blog             # 从 GitHub 拉取模板
cd blog
npm install                # 安装博客本体依赖
```

安装成功的验证输出长这样——hexo-cli 与各组件版本齐刷刷列出来，就是 ready 的信号：

![hexo-cli 安装成功，hexo -v 输出版本列表](hexo-install-success.png)

三个容易踩的坑：

1. `-g` 必须连写，写成 `- g` 会参数解析错误；
2. 全局包装完后如果提示命令不存在，重开终端让 PATH 刷新；
3. **`hexo init` 在当前目录创建项目**——在 `C:\Windows\system32` 里跑就会把博客建进系统目录，务必先 `cd` 到目标盘。

坑之外还有个真实插曲：我一度跳过 `npm install -g hexo-cli` 直接敲 `hexo -v`，PowerShell 只回了我一个红色 CommandNotFoundException。所以"命令不存在"不一定是 PATH 没刷新，也可能是**根本还没装**——先回头看安装那步有没有漏：

![跳过安装直接执行 hexo -v 的报错现场](hexo-command-not-found.png)

### 3.4 目录结构速览

```
blog/
├── _config.yml        # 站点配置（标题、语言、部署方式都在这）
├── source/
│   └── _posts/        # 所有文章的 Markdown 放这里
├── themes/            # 主题
├── scaffolds/         # 新文章的模板
└── public/            # hexo generate 的产物，部署就传这个目录
```

日常只需要关心两个地方：`_config.yml`（配置一次）和 `source/_posts/`（写文章就往这扔）。

## 四、本地验证：确认环境真的跑通了

### 4.1 启动与访问

```powershell
hexo server    # 启动本地预览服务
# INFO  Hexo is running at http://localhost:4000/
```

浏览器打开 `http://localhost:4000`，能看到默认主题（landscape）+ 示例文章，说明整条流水线通了：

![本地预览跑通：landscape 主题首页](hexo-server-running.png)

### 4.2 用"写一篇文章"验证完整闭环

```powershell
hexo new post "我的第一篇博客"
```

命令在 `source/_posts/` 生成带 front-matter 的 Markdown 文件，VS Code 里写几行正文保存，**刷新浏览器文章立刻出现**——这就是 Hexo 的工作流：写文件 → 自动渲染 → 实时预览。

### 4.3 热更新范围

| 改动内容 | 生效方式 |
|---|---|
| Markdown 文章、主题 CSS | 保存后刷新浏览器即可 |
| `_config.yml` 站点配置 | 必须重启 server（Ctrl+C 后重新 `hexo server`） |

### 4.4 中文化

`_config.yml` 的 Site 区域改三行，重启后界面全中文：

```yaml
title: 我的博客
author: 你的名字
language: zh-CN
```

顺手删掉示例文章 `source/_posts/hello-world.md`，博客就是干净的白纸了。

## 写在最后

整个过程从装环境到本地跑通，实际耗时不到一小时。最大的感受是：**工具选对了，坚持成本就低**——以前觉得"写博客"是一件有仪式感的大事，现在它和"写日报"的成本完全一样，都是写一个 Markdown 文件的事。

部署上线后，我会把这次的完整过程作为第一篇文章发出来——也就是你现在看的这篇。
